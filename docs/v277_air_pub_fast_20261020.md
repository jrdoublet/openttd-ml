## 1. Contexte et profil mesuré

Sur une partie de 1 an à 256² (graine 42), pour un total d'environ 66 M d'opcodes/an :
- **Publication AIR incrémentale** (`OpexAir0310PublishIncremental`, `projects_update.nut`, 308 appels/an) : **10,9 M opcodes** (~35 k opcodes/appel) :
  - `pub.filter` : 6,3 M opcodes ;
  - `pub.partition` : 1,6 M opcodes ;
  - `pub.insert` : 1,5 M opcodes ;
  - `pub.recount` : 0,6 M opcodes.
- **Re-sélection** (`OpexReselectProjects`, `projects_selection.nut`, 193 appels/an) : **12,1 M opcodes**, dont **4,4 M opcodes** dans le filtre `OpexAir0310FilterAirAlternativesStillValid` (`projects_generation.nut`).

Deux redondances identifiées :
1. **Publication.** À chaque appel, la fonction historique reparcourait tout le vivier (`projects.candidateGroups`). Pour chaque projet aérien déjà publié, elle rappelait `OpexV141PublishedAirStillValid`, `OpexV141RefreshPublishedAir`, recalculait `OpexProjectKeyFor`, reconstruisait toutes les listes et la table de vivier, puis ré-exécutait `OpexProjectsRecountGroups`.
2. **Filtre de re-sélection.** `OpexAir0310FilterAirAlternativesStillValid` appelait `OpexAirBatchPlanStillLive` (`task_air.nut`), qui bouclait sur toutes les lignes pour chaque plan (`OpexAirTownServed` pour A et B, `OpexAirBatchHubHasCapacity`, puis boucle de détection de paire déjà desservie). Or un prédicat indexé existait déjà : `OpexAirBatchPlanStillLiveIndexed`, avec `OpexIncrRevalidateIndexContext(lines)` (V156), utilisé à la sélection incrémentale mais pas à la re-sélection.

## 2. Deux mécanismes implémentés

### A. Publication rapide (`OpexAir0310PublishIncremental`, `projects_update.nut`)

Quand `V277_AIR_PUB_FAST >= 1` et `priorRaw` est vide (cas nominal hors étape héritée `OPEX_STAGE_AIR_RAIL` ; si `priorRaw` est non vide, repli historique conservé) :
- **Insertion directe dans `candidateGroups` :**
  Pour chaque projet neuf (`pendingNew[slotKey]`), on insère l'objet dans la liste `projects.candidateGroups[slotKey]` juste avant le premier projet tardif (`OpexAir0310ModeIsLate`, c'est-à-dire mode `water` ou `fleet`), ou en fin de liste si aucun projet tardif n'est présent. Si la clé est absente, la liste est créée.
  Ordre résultant strictement identique au chemin historique :
  1. Projets non-aériens non-tardifs (rail, route) ;
  2. Projets aériens déjà publiés (dans leur ordre initial) ;
  3. Projets aériens neufs (dans leur ordre d'émission) ;
  4. Projets tardifs (eau, flotte).
- **Maintien incrémental des statistiques :**
  Au lieu de reparcourir tous les groupes avec `OpexProjectsRecountGroups` (0,6 M opcodes) :
  - Si la clé est nouvelle : `odProjects++`, `modeCandidates++` (modeAlternatives inchangé car longueur 1) ;
  - Si la clé existe déjà : `modeCandidates++`, `modeAlternatives++` (`odProjects` inchangé) ;
  - `projects.all = projects.stats.odProjects`.
- **Mise à jour paresseuse de `planningOpcodes` et `economicsDate` :**
  Les projets neufs reçoivent leurs valeurs lors de leur création dans `OpexProjectFromAir`. Les projets déjà publiés conservent leurs champs sans réécriture O(N). `projects.airOpsPerPlan` et `projects.airEconomicsDate` sont stockés sur `projects`.

### B. Filtre de re-sélection indexé (`OpexAir0310FilterAirAlternativesStillValid`, `projects_generation.nut`)

Quand `V277_AIR_PUB_FAST >= 1` et `C83_FIXES && lines != null` :
- Le contexte indexé `ctx = OpexIncrRevalidateIndexContext(lines)` est construit **une seule fois** par appel, avant la boucle `foreach (project in alternatives)`.
- Dans la boucle, chaque plan est testé via `OpexAirBatchPlanStillLiveIndexed(plan, lines, ctx)` au lieu du balayage O(lignes) `OpexAirBatchPlanStillLive(plan, lines)`.
- **Préservation intégrale du cache mensuel de sites :** `OpexAir0310SiteValidityBegin(stationLimitedTowns)` et `OpexAir0310SiteValidityOk` sont conservés tels quels. `OpexAirSiteStillBuildableIndexed` (cache par appel) n'est pas utilisé (pour éviter les écarts mesurés en V157).

## 3. Preuves d'équivalence par lecture

### 3.1 Équivalence de validité du payload aérien

Dans `projects_builders.nut` (`OpexProjectFromAir`, lignes 268-271) :
```squirrel
  if (economics.profitAnnual <= 0 || economics.revenueAnnual <= 0 ||
      economics.capital <= 0) return null;
  if (decisionEconomics.profitAnnual <= 0 || decisionEconomics.revenueAnnual <= 0 ||
      decisionEconomics.capital <= 0) return null;
```
Dans `projects_update.nut` (`OpexV141PublishedAirStillValid`, lignes 308-316) :
```squirrel
  local economics = payload.economics;
  if (economics.profitAnnual <= 0 || economics.revenueAnnual <= 0 ||
      economics.capital <= 0) return false;
  local decisionEconomics = (("decisionEconomics" in payload)
      && payload.decisionEconomics != null) ? payload.decisionEconomics : economics;
  if (decisionEconomics.profitAnnual <= 0 || decisionEconomics.revenueAnnual <= 0 ||
      decisionEconomics.capital <= 0) return false;
  return true;
```
**Démonstration :**
Tout projet non-nul renvoyé par `OpexProjectFromAir` satisfait par construction :
`profitAnnual > 0`, `revenueAnnual > 0` et `capital > 0` sur `economics` et `decisionEconomics`.
Comme le payload d'un plan aérien est immuable en cours de simulation (ses prédictions économiques ne sont pas modifiées après le scan), `OpexV141PublishedAirStillValid(created.payload)` est vrai à 100% à l'insertion et aux publications suivantes. L'appliquer à l'insertion ne rejette aucun projet et garantit l'invariant sans reparcours.

### 3.2 Équivalence de la clé de vivier

Dans `projects_models.nut` (`OpexProjectKeyFor` / `OpexProjectPairKey`, lignes 26-36) :
Pour un projet aérien : `kind = "pax"`, `cargo = catalog.paxCargo`, `src = plan.siteA.town.tile`, `dst = plan.siteB.town.tile`.
La clé est formée par `kind + "|" + cargo + "|" + min(src, dst) + "|" + max(src, dst)`.
`OpexV141RefreshPublishedAir` ne réécrivait que `cargo = catalog.paxCargo`, qui est identique au cargo d'origine. Les tuiles de ville et le type pax sont invariants. La clé d'un projet ne change donc jamais (`freshKey == slotKey` toujours vrai).

### 3.3 Équivalence ligne à ligne des prédicats du filtre (historique vs indexé)

1. **Dessertes de ville (`OpexAirTownServed` vs `OpexAirTownServedIndexed`) :**
   - Historique : pour chaque ligne `mode == "air"`, teste `AIMap.DistanceManhattan(town.tile, line.originA/B) < 15`.
   - Indexé : `ctx.airOrigins` contient tous les `line.originA/B` des lignes `mode == "air"` (tuiles valides). `OpexAirTownServedIndexed` teste exactement `AIMap.DistanceManhattan(town.tile, orig) < 15` avec seuil 15 identique et mémorise le résultat par `town.tile`.
2. **Capacité hub (`OpexAirBatchHubHasCapacity` vs `OpexAirBatchHubHasCapacityIndexed`) :**
   - Historique : compte les lignes dont `AIStation.GetStationID(line.stationA) == station || AIStation.GetStationID(line.stationB) == station`.
   - Indexé : `ctx.airHubRouteCounts` incrémente le compteur pour chaque station distincte de ligne (`stA` et `stB != stA`). Le total de routes par station est identique. Les plafonds `AIAirport.GetAirportType` et `OpexAirAirportMaxRoutes` sont identiques.
3. **Paires de lignes déjà ouvertes :**
   - Historique : teste si `(line.originA == siteA.town.tile && line.originB == siteB.town.tile) || (line.originA == siteB.town.tile && line.originB == siteA.town.tile)`.
   - Indexé : `ctx.airLinePairs` contient `originA|originB` et `originB|originA` pour toute ligne aérienne. `pairKey = siteA.town.tile + "|" + siteB.town.tile` dans `airLinePairs` est une correspondance exacte.

### 3.4 Lecteurs de `planningOpcodes` et `economicsDate`

  - `task_water.nut:39` : identique pour le panneau eau `OW|...`.
- `economicsDate` :

Choix retenu : les projets reçoivent leurs valeurs lors de la création initiale dans `OpexProjectFromAir`. En publication rapide, `projects.airOpsPerPlan` et `projects.airEconomicsDate` sont tenus à jour sur l'objet `projects`. Les projets existants conservent leur valeur d'origine sans réécriture O(N).

## 4. Mode 2 : Vérification et contrôle d'équivalence au moteur

Le mode `v277_air_pub_fast = 2` exécute simultanément les deux chemins et conserve le résultat historique :

1. **En publication :**
   - Construit le résultat rapide dans une table isolée `v277FastGroups` et incrémente `v277FastStats`.
   - Exécute le chemin historique complet sur `projects.candidateGroups` (`rebuilt`).
   - Compare :
     - Nombre de clés et présence mutuelle de chaque clé ;
     - Longueur de chaque liste de projets ;
     - Identité de référence (`==`) et ordre de chaque projet dans chaque liste ;
     - `projects.all == v277FastStats.odProjects` ;
     - `projects.stats.odProjects`, `modeCandidates`, `modeAlternatives`.
   - Si une divergence apparaît, journalise sous `V277_CHECK` via `OpexDecide` (et `AILog.Warning` si `DECISION_LOG` est faux).
   - Conserve le vivier et les statistiques du chemin historique.
2. **En re-sélection :**
   - Évalue `histVerdict = OpexAirBatchPlanStillLive(plan, lines)` et `fastVerdict = OpexAirBatchPlanStillLiveIndexed(plan, lines, ctx)`.
   - Si `histVerdict != fastVerdict`, journalise :
     `V277_CHECK filter townA=<id> townB=<id> hist=<verdict> fast=<verdict>`.
   - Conserve et applique le verdict historique `histVerdict`.
