# V95 — AIR post-1973 : petites villes et seconds slots

État : **sonde passive implémentée, défaut 0 ; smoke + diagnostics solo/shared 3×6 terminés ; aucun 5×6 causal justifié à ce stade**.

## Audit du chemin courant

Le problème n'est pas un simple manque de villes dans le pool AIR. Sur 256², C78.3
laisse déjà passer pratiquement toutes les villes. En revanche, OpexAirPlansFindSites
écarte plusieurs populations **avant** toute économie de ligne :

1. une ville déjà marquée servie est rejetée "origin_served", sauf le cas étroit du second slot C83.1 ;
2. une ville non servie de moins de 600 habitants est rejetée "town_pop_small" pour les grands aéroports quand V93 est à 0 ;
3. seulement ensuite OpexAirFindSite cherche une ancre et peut conclure "no_site_slot", "no_site_budget" ou "no_site_terrain".

Conséquence : pour "origin_served" et "town_pop_small", le code courant ne connaît ni site constructible, ni coût de terrassement, ni avion C68, ni profit prédit.

Le modèle courant reste inchangé : le bras hub→site évalue la demande par le proxy population × TOWN_CATCHMENT_SHARE_PCT, puis C68 maximise le profit annuel. V93.1 n'est pas réactivé.

AITile.GetCargoProduction compte des **tuiles productrices**, pas des passagers/mois. V95 publie donc séparément :

- pax_prod / mail_prod : production réelle du mois précédent via AITown.GetLastMonthProduction ;
- pax_tiles / mail_tiles : couverture physique du site en tuiles productrices ;
- pax_site_est / mail_site_est : estimation de production captée à partir de la production moyenne par maison.

## Sonde v95_air_post73_probe

Réglage booléen, **défaut 0**. La sonde :

- ne tourne qu'à partir de 1973, au plus une fois par année de jeu ;
- ne tourne que pendant une génération AIR complète, jamais lors d'un replan C83 ciblé ;
- ne remplit pas AIR_SITE_CACHE, n'ajoute rien à ctx.sites et n'injecte aucun projet.

Familles :

- small : population < 600, rejet courant "pop_floor" ;
- second : ville déjà servie mais hors exception C83.1, rejet courant "origin_served" ;
- small_second : recouvrement des deux.

Chaque ligne V95_AIR_POST73 phase=town publie population, site, production PASS/MAIL, couverture, coût estimé, TownID physique du slot, slots restants, aéroports Opex, présence concurrente inférée, meilleur raccordement hub→site, avion choisi par C68, profit, capital, ROI et disponibilité de caisse.

competitor_airports vaut le nombre de slots occupés par un tiers inféré de l'état physique. Dans un duel à deux compagnies, ce tiers est AAAHogEx ; hors duel il faut le lire comme « concurrent ».

site_cost_est = airport_price + level_cost. Le terrassement est testé en AITestMode ; le nettoyage d'arbres n'est pas inclus.

Le choix hub→site est intentionnel : il mesure l'exposition post-1973 d'un réseau déjà constitué. Les paires de deux nouveaux petits sites constituent une population différente.

## Validation et protocole

- contrats : sweeps/test_v95_air_post73_probe.py ;
- analyseur : sweeps/analyse_v95_air_post73.py ;
- extraction dédiée : sweeps/diag_v95_air_post73.py, à lancer sous Linux/Docker pour que l'injection `-d script=4` soit fiable avec multiprocessing ; sous Windows `spawn`, le monkeypatch de `openttdlab.subprocess.check_output` ne se propage pas proprement aux workers.

Ordre : smoke moteur, diagnostic solo sur quelques graines jusqu'après 1973, puis 5×6 causal uniquement si une population suffisamment exposée produit un filtre minimal précis. Aucun 20×10 avant un 5×6 favorable.

Le plancher global V93 reste inchangé.

## Mesures du 2026-09-26

### Smoke Linux 1×4, graine 42

`results/smoke_v95_air_post73_1x4_linux_20260926.json` est sain et émet bien la sonde en 1973 :

- **39 occasions** ignorées par le chemin courant ;
- 17 petites villes `<600`, 23 villes `origin_served` (une ville appartient aux deux familles) ;
- **30 sites** trouvent un raccordement hub→site rentable et finançable au modèle courant ;
- 8 extensions sont déjà `slot_closed` ; un seul `site_terrain` ;
- aucun candidat ne dépasse **50 k£/an** quand l'extrémité nouvelle est réévaluée avec la production estimée de son bassin.

Ce smoke valide donc l'**exposition** et le chemin de mesure, pas un levier économique.

### Solo 3×6, graines 42 / 100 / 999

`results/diag_v95_air_post73_solo_3x6_20260926.json` contient **366 événements** post-1973 et **290 candidats shadow**. L'exposition est largement suffisante pour décider si un filtre simple existe.

Pour les villes `<600`, le modèle courant est optimiste : sur 154 candidats `small`, le profit courant médian est **16,6 k£/an** contre **10,8 k£/an** avec l'estimation de bassin ; la production PASS estimée au site vaut 38,5/mois en médiane. Sur la famille agrégée `<600` (incluant `small_second`), **0 cas** atteint 50 k£/an mesuré. Le coût de site n'est pas le verrou principal : médiane ≈ **18,9 k£**.

Pour les seconds slots physiques Opex en solo : **141 événements**, 138 sites, 132 profits mesurés positifs, mais profit courant médian **23,9 k£/an** contre seulement **8,7 k£/an** mesuré. Aucun cas ne dépasse 50 k£/an mesuré ; aucun ne satisfait le critère strict « modèle mesuré non dégradé par rapport au modèle courant ET contribution positive du nouveau site au-delà du hub seul ».

Conclusion solo : ouvrir les petites villes ou les extensions Opex sur un simple seuil de production/coût reproduirait le défaut de V93. Le proxy population surestime précisément la poche que l'on cherchait à libérer.

### Duel passif partagé 3×6 contre AAAHogEx

`results/diag_v95_air_post73_shared_3x6_20260926.json` donne **343 événements**, dont 149 déjà `slot_closed`. La concurrence crée bien une population territoriale supplémentaire :

- **60 vrais seconds slots concurrents** (`slots_remaining=1`, Opex absent, concurrent présent), 26 couples graine-ville ;
- 60/60 ont un site et un profit courant positif ; 57 ont un profit mesuré positif, 51 sont finançables ;
- le profit mesuré de la **route entière** peut dépasser 50 k£/an (19 événements), parce que le hub Opex existant apporte déjà une forte demande ; cette métrique seule ne mesure donc pas la valeur du nouveau site ;
- la contribution marginale estimée du nouveau site, `measured_profit - hub_only_profit`, vaut seulement **≈3,9 k£/an en médiane** ;
- **0/60** satisfait le critère strict « profit mesuré ≥ profit courant ET contribution du nouveau site > 0 » ;
- même sur les seuils de captage, aucun second slot concurrent à profit mesuré ≥50 k£ n'atteint `pax_site_est >= 50`.

La famille `<600` en duel montre la même ambiguïté : 43 événements ont une route entière mesurée à ≥50 k£/an, mais seulement **3** passent le critère strict non-dégradé + incrémental, dont **2 finançables**. Ce n'est pas une population assez propre pour définir un filtre causal général.

## Décision expérimentale

**Ne pas lancer de 5×6 causal V95 sur l'état courant.** L'exposition est abondante, mais le mécanisme économique visé n'est pas démontré : la production/couverture du nouveau site contribue peu au profit, tandis que les gros chiffres observés en duel viennent surtout du hub déjà existant. C83.1 reste le levier territorial qualifié pour les six grandes villes ; l'élargir implicitement aux petits marchés serait une autre politique.

Les réglages causaux V95 présents à défaut 0 ne doivent pas être promus ni benchmarkés tant qu'un filtre ne sépare pas proprement la **valeur marginale du nouveau site** de la valeur du hub existant. Une prochaine sonde utile serait de relier le second slot concurrent à la **demande réellement résiduelle/captable dans la ville cible** ou à une valeur territoriale explicite ; ne pas réactiver V93 globalement.

Limite de la mesure actuelle : V95 sonde le premier combo `large` rencontré de l'année (ordre catalogue INTERNATIONAL → METROPOLITAN → LARGE). Sur ces diagnostics 256², les échecs `site_terrain` sont rares, donc cette approximation n'explique pas le verdict ; elle devra être levée si un futur diagnostic porte spécifiquement sur la géométrie des sites.
