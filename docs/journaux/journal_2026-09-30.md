### R22 — relance idempotente tant que l'arrêt au dépôt est actif

Après les contrôles existants de vente, timeout et intervalle de 90 jours, la
relance consulte `AIOrder.IsGotoDepotOrder` et `GetOrderFlags` avec **ORDER_CURRENT
directement**, sans `ResolveOrderPosition` : les détournements manuels sont hors
liste. `OF_STOP_IN_DEPOT` entraîne l'attente sans nouvelle commande ; flags
inconnus entraînent également l'attente prudente. Un simple ordre d'entretien
reste convertible en arrêt via `SendVehicleToDepot`. Ordre disparu : la relance
reste possible. Date/compteur ne changent qu'après succès, par `rawset`, compatible
avec les tickets table auxquels ces slots manquent. Les tickets legacy entiers,
le calendrier, les ventes et l'exemption de rééquipement V92 sont conservés.

API vérifiée par lecture du code OpenTTD **15.3** : `script_order.hpp/.cpp`,
`script_vehicle.cpp`, puis extrait ciblé `Vehicle::SendToDepot` de `vehicle.cpp`.
La commande annule un ordre d'arrêt déjà actif ; sans drapeau d'arrêt, elle le
convertit en arrêt. Cette lecture n'est pas une exécution NoAI et aucun extrait
tiers n'est copié dans OpexAI.

**Limites :** l'envoi initial dans le handler d'événement et le timeout ne sont
pas refondus. Notamment, le timeout historique réintègre l'inventaire et relance

### R4 : diagnostic de l'inertie

Mécanisme (`scheduler_tasks.nut`) : la tranche reçoit `sliceBudget = GetOpsTillSuspend()` (≤ quota d'un tick), mais `OpexAirPlans` ne teste le budget qu'entre deux paires. Une paire coûte plus qu'un tick (tranches médianes ~40 k opcodes, max ~98 k sur 167) : la VM suspend donc pendant la tranche, `GetTick()` avance et `OpexC121CatalogCanContinue` refuse l'enchaînement (`chained_slices=0`). Ce n'est pas un bug du prédicat : l'enchaînement intra-tick est inatteignable à la granularité paire.

Décision : pas de changement de code (option expérimentale, défaut désactivé, C115 intact). Retirer la garde de tick transformerait les tranches en passe monolithique ; rendre l'enchaînement possible exigerait des points d'arrêt à l'intérieur d'une paire, chantier distinct. Les gains de cadence attribués à R4 sont à attribuer au découpage lui-même, pas à l'enchaînement. R4 est clos comme **garde-fou correct, sans effet mesurable**.
