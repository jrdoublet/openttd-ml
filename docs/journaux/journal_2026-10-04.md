### Autopsie de la garde géométrique — cause du rail perdu

Demande utilisateur : vérifier d'abord le correctif, puis isoler le mécanisme qui fait
perdre du rail. Audit statique + isolations causales 20×5 + trace script ciblée.

**Audit du correctif.** La convention `[lead, station_exit]` est confirmée dans le
pathfinder V90 : la source est construite `station_exit -> lead`, et à l'arrivée le
pathfinder n'accepte `lead` que si `station_exit` est un voisin valide, puis l'ajoute au
chemin. Le matching exact utilise donc les bons indices. Le retour immédiat vers le
parent est interdit dans `_Neighbours`, ce qui réfute l'hypothèse d'un `lead` supprimé
par la simplification A-B-A. Dans la trace ciblée 4×5 sous `script=4`, **0 NOMATCH**.
Le correctif n'est donc pas en train de casser silencieusement les chemins ; il répare
réellement des poses. Exemple graine 54321 : la paire pax `22088->4686` fait
`STNFAIL` le 25/09/1972 dans l'historique, mais est **OK** le 24/10/1972 avec identité
exacte. Graine 512 : `45596->44387` échoue plusieurs fois en `TRKFAIL` dans le témoin,
mais est **OK** le 24/08/1973 avec identité exacte. Graine 123456 : le fret
`28980->44575` passe de `STNFAIL` à **OK**.

Trois sous-interrupteurs diagnostiques ont été ajoutés sous `rail_geometry_guard`
(valeur 1 = comportement candidat actuel) : `rail_geometry_exact_identity`,
`rail_geometry_prefilter`, `rail_geometry_pair_memory`. Le garde principal reste à

**Isolation mémoire de paire** — `results/railgeom_pairmem_iso_20x5_20261004.json`,
garde complète vs même garde sans mémoire : sans mémoire, `profit_year` **−12,2 k£/an**

n'est donc pas la cause du rail perdu ; elle évite plutôt quelques répétitions nuisibles.

**Isolation préfiltre** — `results/railgeom_prefilter_iso_20x5_20261004.json`, identité
exacte dans les deux bras, mémoire OFF, préfiltre ON vs OFF : couper le préfiltre donne

**Isolation identité exacte** — `results/railgeom_identity_iso_20x5_20261004.json` :
identité exacte seule contre reconstruction historique. Effet moyen faible :
`profit_year` **+8,1 k£/an**, gap Opex−AAA **+45,5 k£/an**, mais fin 1974 **−0,2 gare
rail / −0,15 train**. L'effet n'est pas uniforme : 54321 perd 4 gares/2 trains, 512 en
perd 2/2, 424242 en perd 2/1, tandis que 4096 gagne 2 gares/1 train et 123456 en gagne
4/2. C'est donc un embranchement de trajectoire, pas un filtre systématique.

La trace ciblée `results/railgeom_identity_trace_4x5_20261004_r2*` explique cet
embranchement. Sur 54321, le succès réparé `22088->4686` fin 1972 marque ses origines
comme desservies. Le générateur de candidats rail applique encore une **exclusivité par
origine** : pax `if (sa != null || sb != null) continue`, fret industrie pareil, fret
vers ville pareil. Il élimine donc une paire dès qu'**UNE SEULE** extrémité est déjà
desservie. C'est plus strict que `OpexCandidateStillValid` pour le rail, qui ne rejette
quand **LES DEUX** extrémités sont desservies, et contradictoire avec le commentaire de
`candidates.nut` annonçant justement ce relâchement.

ferme ensuite le vivier rail** via l'exclusivité d'origine. Même signature sur les
graines 512/123456 : une ancienne pose échouée devient réussie, puis l'ordre des projets
et le réseau futur divergent. L'AIR supplémentaire est une **réallocation secondaire**
du capital devenu disponible, pas la cause première.

rail : aligner la génération avec la règle déjà utilisée en revalidation (`both served`)
ou autoriser explicitement les extensions joignables. Ce changement est comportemental
et devra être isolé derrière un réglage défaut 0 avant banc long rail.

calculés avant la recherche et réutilisés après celle-ci, une géométrie exacte devenue obsolète ou

(paire + anchors/steps/leads), pas la paire entière.
