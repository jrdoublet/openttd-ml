# Journal 2026-10-05 — rail `origin_served`

## Correctif candidat : réutilisation d'une origine rail déjà servie

Contexte : la garde géométrique rail est mécaniquement saine, mais un succès plus tôt dans la partie
réduit ensuite le vivier parce que le générateur rejetait toute paire avec `sa != null || sb != null`,
alors que la revalidation rail ne rejette que si les deux extrémités sont servies.

Implémentation derrière réglages à défaut inchangé :

- `rail_origin_reuse=0` par défaut. À 0, comportement historique strict ; à 1, une paire avec une
  seule extrémité servie peut être considérée ; deux extrémités servies restent rejetées.
- `rail_origin_reuse_fallback=0` par défaut. À 1, la génération normale reste stricte ; une seconde
  passe ne calcule les extensions qu'en cas de vivier frais inférieur à `TOP_K`, et ne les utilise
  que pour remplir les places manquantes.
- `rail_origin_reuse_pax=1` et `rail_origin_reuse_freight=1` sont des sous-toggles diagnostiques,
  inertes tant que le parent reste à 0 ; leurs valeurs 1 reproduisent le candidat parent.
- La jointure exige un service non ambigu, une géométrie de quai persistée, même `kind`/cargo, et
  pour le fret le même rôle A/B. Le constructeur supporte une jointure sur A ou B sans inverser le
  flux fret. `BASIN_SHARE` reste appliqué avant le filtre.
- `rail_geometry_guard` n'a pas été modifié.

Validation statique après la scission pax/fret : **113/113 tests `test_*rail*.py` OK** ;
`git diff --check` OK hors avertissements CRLF préexistants.

## Ce que les bancs ont montré

### 1. OR→AND seul : mécanisme confirmé, politique insuffisante

Smoke ciblé 4×5 (`54321/512/123456/4096`, `decision_log=1`) : `origin_served` baisse sur 4/4,
`VIVIER_GEN kept` monte, pas de nouvelle explosion `TRKFAIL`. Mais les candidats récupérés tombaient
ensuite massivement en `too_close_no_join` : ex. 54321 **5→106**, 512 **30→68**.

Après transport explicite du `StationID`/quai/ligne et compatibilité historique de jointure, le
raccordement physique fonctionne. L'ancien `station_join` du 29/08 a été retrouvé dans Git : même
famille causale, déjà connue pour augmenter fortement la construction sans garantir la valeur.

### 2. Priorité égale rejetée ; fallback paresseux retenu comme forme correcte

Le relâchement à priorité égale perturbe le portefeuille et réduit le rail au 20×5. Le fallback
paresseux corrige ce défaut : on ne paie pas l'économie des extensions tant que le vivier frais
suffit, et elles ne remplacent jamais un candidat à deux origines libres.

20×5 solo propre du fallback complet : signal de mécanisme favorable (environ **+1,45 train** et
**+1,85 gare rail** par graine, `profit_year` +72,8 k£/an moyen), mais ce n'est pas une preuve en
carte partagée.

### 3. Carte partagée 40×5 : le candidat complet est quasi-neutre économiquement et améliore le gap

`results/rail_origin_reuse_fallback_gateA5_20261005.json` :

- `profit_year` variante − référence : **+56 058,8 £/an**, 24V/16D, Wilcoxon **p=0,0451**,
  IC95 bootstrap **[+3,3 k ; +109,4 k]** ; seuil pré-enregistré +4 % = **56 124,9 £/an**.
  Échec formel `fail_primary` pour seulement **66 £/an** sous le seuil ; ne pas arrondir en succès.
- garde de valeur : passe ;
- gap `profit_year` Opex−AAA : évolution moyenne **+95,4 k£/an**, 26V/14D, non significatif
  (Wilcoxon p≈0,158 ; IC95 traverse 0) ;
- volume rail terminal quasi neutre/légèrement inférieur : 266 trains vs 267 et 486 gares rail vs 492.

Conclusion : cette famille n'est pas le correctif du **volume rail physique** à 5 ans, mais elle agit
sur la trajectoire compétitive.

### 4. Isolation fret/pax : le pax est le levier anti-AAAHogEx

Calibration instrumentée 20×5 : 10 tentatives d'extension uniques observées, **8 pax / 2 fret**.
Les 2 fret réussissent ; le pax a 4 succès sur 8 avec plusieurs recherches/site failures coûteuses.
Le solo pouvait donc faire croire que le pax était le mauvais sous-mode.

La carte partagée dit l'inverse :

- **fret-seul 40×5** (`results/rail_origin_reuse_freight_only_gateA5_20261005_r2.json`) :
  `profit_year` **−55,4 k£/an**, 18V/22D, p≈0,0867, IC95 bootstrap [−110,4 k ; +0,06 k] ;
  évolution du gap AAA **+46,8 k£/an**, 17V/23D, p≈0,735. Rejeté.
- **pax-seul 40×5** (`results/rail_origin_reuse_pax_only_gateA5_20261005.json`) :
  `profit_year` **+39,6 k£/an**, 24V/16D, p≈0,375, IC95 bootstrap [−34,0 k ; +114,3 k] ;
  valeur +2,94 % ; **évolution du gap AAA +225,8 k£/an**, 23V/17D, Wilcoxon **p=0,0381**,
  IC95 bootstrap **[+15,1 k ; +437,9 k]**. Le gain stratégique est donc significatif sur ce banc.
  Algébriquement, +39,6 k£ côté Opex pour +225,8 k£ de gap implique environ **−186,3 k£/an**
  sur le profit AAA relatif au témoin.
- Le pax-seul n'augmente pas le volume rail Opex : environ **−0,28 train**, **−0,78 gare rail**,
  avec +1,25 avion en moyenne. Son effet est compétitif/territorial, pas un redressement physique du rail.

## Verdict / suite

1. **Aucun défaut n'est activé** : `rail_origin_reuse` reste 0, `rail_origin_reuse_fallback` reste 0 ;
   aucune porte B n'est lancée.
2. Ne pas supprimer le pax sur la foi du solo : en duel partagé, c'est le sous-mode qui améliore
   significativement le gap AAA.
3. Ne pas présenter cette famille comme le correctif du décrochage physique du rail : à 40×5 le
   nombre de trains/gares ne progresse pas de façon robuste.
4. Prochaine question causale utile : **pourquoi les extensions pax rail réduisent-elles le profit
   AAAHogEx alors qu'elles n'augmentent pas notre volume rail ?** Instrumenter la territorialité rail
   (TownID de l'extrémité neuve, présence/prise concurrente autour de cette ville, date de première
   desserte Opex/AAA) avant d'introduire un bonus de classement. Réutiliser si possible les primitives
   territoriales déjà présentes côté AIR ; pas de nouveau coefficient arbitraire.

Pas de commit/push.

## Qualification one-pass compacte — protocole demandé le 05/10

Pré-enregistrement avant mesure : branche `c121-catalog`, HEAD `bad7e7b`, working tree sale préservé.
Le candidat est l'implémentation courante **one-pass deferred reuse** compacte ; aucun changement de
défaut. Bras de référence `OpexAI[rail_geometry_guard=1,rail_origin_reuse=0]`, bras candidat
`OpexAI[rail_geometry_guard=1,rail_origin_reuse=1,rail_origin_reuse_fallback=1,rail_origin_reuse_pax=0]`.

À la demande explicite de l'utilisateur, la porte courte est un **40×5** `gain_short` (horizon alternatif
fixé avant mesure) : `profit_year`, delta moyen ≥ 4 % du profit moyen référence terminal, IC95 bootstrap
borne basse > 0, Wilcoxon exact bilatéral p < 0,05, garde `company_value` −5 %. Si elle passe, enchaîner
une porte B standard **20×10** `non_erosion` : borne haute IC95 ≥ 0, garde `company_value` −5 %, sans
minimum de gain positif. Une seule campagne Docker à la fois, maximum 10 CPU / 10 workers.

Résultats :

- 40×5 `results/rail_origin_reuse_onepass_compact_gateA5_20261005.json` : 40/40 paires complètes,
  `profit_year` delta moyen **−4 902 £/an**, médiane 0, V/D/E 8/15/17, Wilcoxon p=0,3765,
  IC95 bootstrap **[−24 343 ; +15 370] £/an**, seuil +4 % **55 348 £/an** ; garde valeur
  ratio des moyennes **+0,040 %**. Verdict **`fail_primary`**.
- Porte B 20×10 `results/rail_origin_reuse_onepass_compact_gateB_20261005.json` lancée malgré l'échec
  court à la demande explicite de l'utilisateur, donc mesure longue diagnostique : 20/20 paires complètes,
  `profit_year` delta moyen **−36 233 £/an**, médiane −34 831, V/D/E 6/13/1, IC95 bootstrap
  **[−118 910 ; +51 416] £/an** ; garde valeur ratio des moyennes **+0,307 %**. Verdict
  **`pass` `non_erosion`** car la borne haute de l'IC95 reste ≥0.
- Les deux artefacts ont `comparison_complete=true`, `adoption_sample_complete=true` et
  `metric_coverage_complete=true`. La famille reste **non adoptable** : la porte courte a échoué ;
  le passage de B ne l'annule pas. Aucun défaut activé, aucun commit/push.

## Autopsie causale graine/mois après le recul du signal

Le point haut apparent `freight_fastpath2` (`rail_origin_reuse_freight_fastpath2_autopsy_4x5_20261005_r4`)
était **+78,1 k£/an** avec **+97,5 k£/an de gap**, mais il ne correspond pas à un succès physique du
mécanisme : sur ses quatre graines, **0 tentative et 0 construction `reuse=1`**. Le signal est porté
uniquement par 802204 (+88,7 k£, gap +305,0 k£) et 983759 (+223,8 k£, gap +85,1 k£), dont les
portefeuilles divergent après des coûts de génération/logging sans raccord reuse. Ne pas chercher à
« récupérer » ce +78 k£ : c'est un faux positif de trajectoire/scheduler.

Même diagnostic sur les anciens 40×5 : full, pax-only et freight-only ont une première différence
mesurable sur **40/40 graines dès 1970**, alors que la calibration instrumentée des vrais raccords n'a
observé que **10 tentatives reuse, toutes en 1974** (8 pax / 2 fret ; succès 4/8 pax et 2/2 fret).
L'ancien pax-only (+225,8 k£ de gap) est donc lui aussi fortement contaminé par la cadence ; il reste
une hypothèse territoriale à retester, pas une preuve causale.

Le one-pass compact courant supprime l'essentiel de ce bruit précoce : à 5 ans, 17/40 graines restent
exactement neutres ; première différence sur 1 graine en 1971, 4 en 1972, 7 en 1973 et 11 en 1974.
Mais les 23 graines activées restent légèrement défavorables en moyenne (profit ≈ −8,5 k£/an, gap
≈ −40,4 k£). Les 20 graines canoniques sont plus favorables (+9,8 k£, gap +34,6 k£, 8/20 activées)
que les 20 supplémentaires (−19,6 k£, gap −81,0 k£, 15/20 activées) : forte hétérogénéité de carte.

Contrôle essentiel de répétabilité : porte A 40×5 et préfixe 5 ans de la porte B utilisent le **même
bundle `907963d...`**. Sur les 20 graines communes, 10/20 trajectoires de delta diffèrent entre les deux
exécutions ; le bras référence brut diffère sur 8/20 et la variante brute sur 7/20. L'agrégat 20 graines
reste pourtant proche (+9,8/+34,6 k£ contre +4,7/+33,5 k£ profit/gap). Une conclusion graine par graine
sur une seule exécution n'est donc pas fiable ; conserver les motifs répétés et les agrégats.

Trace mécanistique ciblée 8×5 (`rail_origin_reuse_mechanism_trace_8x5_20261005`, même bundle, mais
`decision_log=1`, donc diagnostic uniquement) sur 17/100/12345/4096/65537/54321/512/1024 : **0
tentative et 0 construction `reuse=1` sur 8/8**. Pourtant plusieurs portefeuilles divergent. 100 et
65537 montrent explicitement plusieurs `DEFER → FINALIZE` avec `reuse_total=0 joinable=0`; 17 et 1024
entrent aussi dans le chemin différé. Le code courant peut donc encore déphaser la partie en payant
l'évaluation d'un fallback qui ne produit aucun candidat physique.

Cause de coût lue dans `candidates.nut` : `OpexRailOriginReuseFinalize` appelle
`OpexRailOriginReuseEvaluateFreight/Pax`, qui **reconstruisent les services puis ré-énumèrent les paires**
pour conclure parfois `joinable=0`. Prochain correctif à instruire avant tout nouveau classement : un
**fast-negative tardif O(nombre de lignes)**, exécuté uniquement une fois le fallback déjà nécessaire,
qui prouve qu'aucune ligne rail existante du même kind/cargo ne possède de quai potentiellement
réutilisable ; dans ce cas retourner immédiatement sans ré-énumérer industries/villes. Il doit être
sans faux négatif et ne pas remettre de travail par paire dans le passage frais (le préflight par paire
avait déjà été réfuté pour perturbation de cadence).

### Fast-negative tardif — implémentation et validation

Implémenté dans `candidates.nut` via `OpexRailOriginReuseHasPotentialLine(lines, kind, cargo)`.
Le helper ne s'exécute qu'au début de `OpexRailOriginReuseEvaluatePax/Freight`, donc **après** que le
fallback reuse est déjà nécessaire. Il ne touche jamais le passage frais. Il ne teste qu'une condition
nécessaire au resolver complet : ligne rail-compatible, même `kind`, cargo compatible (ou cross-cargo),
`lineId`, et au moins une extrémité possédant à la fois quai persistant et StationID valide. Il ne filtre
pas proximité, rôle fret, ambiguïté ni multiline : ces conditions restent au resolver complet, ce qui
garantit qu'un doute devient un faux positif (scan conservé), jamais un faux négatif.

Audit du trace 8×5 précédent : 10/10 `DEFER → FINALIZE reuse_total=0 joinable=0` avaient **zéro ligne
fret du même cargo** au moment du finalize (seed100 ×6, seed65537 ×4). Le garde per-cargo couvre donc
10/10 de ces rescans nuls. Important : ne jamais le mettre globalement en cache avant la rotation
`freightCargo` ; seed17 fournit un near-miss où le cargo initial puis le cargo de fallback ont chacun
leurs propres lignes potentielles.

Validation :

- tests : `39/39` origin-reuse, `132/132` tests rail, `git diff --check` OK ;
- smoke graine100 2 ans, `decision_log=1` : `fast_negative=1` sur le vieux cas nul du 1971-08-29 ;
  référence et variante deviennent **strictement identiques** sur profit, gap, métriques AIR et les
  16 projets choisis ;
- trace fast-negative 8×5 (`results/rail_origin_reuse_fastneg_trace_8x5_20261005`) : l'ancien trace
  diagnostique était à **+79,5 k£/an** moyen ; avec le garde il tombe à **−4,4 k£/an**, confirmant que
  le gros signal venait du coût scheduler parasite ;
- chemin positif préservé : seed65537 produit `reuse_total=3`, `joinable=12` puis **3 vraies tentatives
  `reuse=1`**. Le garde ne les coupe pas. Elles échouent ensuite pour `SITEA`, `SITEA`, `TRKFAIL`, donc
  le prochain obstacle est la constructibilité de ces raccords, pas le fast-negative.

Le fast-negative réduit fortement mais ne supprime pas toute bifurcation diagnostique : dans le trace
8×5, quelques graines divergent encore sans build reuse. Une partie est compatible avec le coût restant
O(lines) + instrumentation `decision_log`; ne pas surinterpréter les amplitudes d'un trace debug.
