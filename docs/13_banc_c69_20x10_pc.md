# C69 étape 4 — lancer le banc 20×10 en duel sur un PC à 10 cœurs

Banc d'autorité C66.4 : `c70_c69` (calibration + levier) contre `c70` (calibration seule), en
duel contre AAAHogEx, 20 graines × 10 ans, apparié. Critère écrit d'avance
(`11_goulot_decision.md` §10, étape 4) : test des signes **≥ 15/20** avec p < 0,05, écart moyen de
`profit_year` **> +50 k£/an**, garde **−5 %** sur `company_value`.

⚠️ **Le duel n'est pas déterministe** (§16.1) : un rejeu du même code s'écarte jusqu'à 18 %. Le
banc se lit au test des signes, pas sur une graine.

## 1. Prérequis (une fois)

- Linux, ou Windows avec WSL2 + Docker Desktop (lancer toutes les commandes dans le shell WSL).
- Docker, git, python3 sur l'hôte.
- Accès internet au premier lancement : OpenTTDLab télécharge OpenTTD 15.3, OpenGFX et deux
  bibliothèques BaNaNaS dans le volume `openttd-lab-home`.
- RAM : compter environ 1 Go par worker. Avec 9 workers, donner **12 Go** au conteneur (≥ 16 Go
  sur la machine).

```bash
git clone git@github.com:jrdoublet/openttd-ml.git   # ou git fetch si déjà cloné
cd openttd-ml
git fetch origin
git checkout c69-goulot-decision
```

**AAAHogEx n'est pas dans le dépôt** (exclu volontairement, `.gitignore`). Le copier depuis le VPS :

```bash
scp -r deploy@<VPS>:~/projects/openttd-ml/ai/AAAHogEx-115 ai/
# Vérifier que c'est bien la même version (depuis la racine du dépôt) :
find ai/AAAHogEx-115 -type f | sort | xargs sha256sum | sha256sum
# attendu : 9921a60266c7ac69ef7d79369329ad71868a1a21b864ef4a0cd1d9a96a46ccfd
```

**Image Docker**, construite avec votre UID pour pouvoir écrire dans `results/` :

```bash
docker build --build-arg UID=$(id -u) --build-arg GID=$(id -g) -t openttd-lab .
```

## 2. Contrôle rapide (≈ 5 min)

Vérifie le téléchargement, la compilation de l'IA et l'écriture des résultats, sur 1 graine × 1 an.

```bash
python3 sweeps/run_c66_reference.py \
  --campaign c69_smoke_pc \
  --policy-id c70 --reference "OpexAI[c70_mode_calibration=1]" \
  --variant "OpexAI[c70_mode_calibration=1,c69_decision_bottleneck=1]" --variant-policy-id c70_c69 \
  --min-useful-primary-delta 50000 --value-guard-max-loss-pct 5 \
  --years 1 --seeds 42 --max-workers 2 --cpus 2 --memory 4g
```

Il doit finir sans `Traceback` et écrire `results/c69_smoke_pc.json`. Le verdict n'a aucun sens
sur une graine. Supprimer ensuite ses fichiers :

```bash
rm -rf results/c69_smoke_pc*
```

## 3. Le banc (≈ 1 à 2 h avec 9 workers)

```bash
python3 sweeps/run_c66_reference.py \
  --campaign c69_step4_c70c69_vs_c70_10y_20seeds \
  --policy-id c70 --reference "OpexAI[c70_mode_calibration=1]" \
  --variant "OpexAI[c70_mode_calibration=1,c69_decision_bottleneck=1]" --variant-policy-id c70_c69 \
  --min-useful-primary-delta 50000 --value-guard-max-loss-pct 5 \
  --years 10 --max-workers 9 --cpus 10 --memory 12g \
  2>&1 | tee results/c69_step4.log
```

- Sans `--seeds`, les 20 graines de référence de `bench_v2.py` sont utilisées.
- **Ne pas modifier l'arbre de travail pendant le banc** : le code de l'IA est lu depuis le dépôt,
  et l'état git est enregistré dans le manifeste (`dirty=0` attendu).
- Une campagne existante n'est jamais écrasée. Pour relancer, changer `--campaign`.
- Pour le suivre : `docker ps`, et le fichier de reprise `results/<campagne>*.jsonl` qui grossit.

**Facultatif, second banc** (C69 + C70 contre le défaut, même durée) : même commande avec
`--campaign c69_step4_c70c69_vs_default_10y_20seeds --policy-id default` et **sans** `--reference`.

## 4. Rapporter

Pousser le résultat sur la branche, ou le déposer sur le VPS :

```bash
git add -f results/c69_step4_c70c69_vs_c70_10y_20seeds.json results/c69_step4.log
git commit -m "mesure(c69): etape 4, banc 20x10 duel"
git push
```

Le verdict se lit dans la dernière partie du journal (test des signes, écart moyen, garde de
valeur), et dans la clé `policy_comparison` du JSON.

## 8. C75 + classement C69 bis (`16_bilan_volume.md` §9)

Combinaison : plusieurs chantiers par passe (`c75_multi_build`) + classement qui bascule du ROI au
profit quand l'entreprise s'enrichit (`c69_decision_bottleneck`, flotte exemptée
`c69_fleet_exempt`, calibration par mode `c70_mode_calibration`). Smoke 2 × 3 ans ici : 2/2 sains
(`results/c75_c69bis_smoke_2x3.json`). Après `git pull`, arbre propre :

```bash
python3 sweeps/run_c66_reference.py \
  --campaign c75_c69bis_vs_default_10y_20seeds \
  --policy-id default \
  --variant "OpexAI[c75_multi_build=1,c69_decision_bottleneck=1,c69_fleet_exempt=1,c70_mode_calibration=1]" \
  --variant-policy-id c75_c69bis \
  --min-useful-primary-delta 50000 --value-guard-max-loss-pct 5 \
  --years 10 --max-workers 9 --cpus 10 --memory 12g \
  2>&1 | tee results/c75_c69bis.log
```

À noter pour la lecture : C69 calcule τ comme 365 / chantiers de l'année. Sous C75, les chantiers
sont plus nombreux, donc τ et K_dec plus petits : la bascule vers le profit est plus tardive
qu'avec C69 seul. C75, lui, utilise τ_pass (durée réelle entre deux passes).
